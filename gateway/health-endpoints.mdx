Qorven exposes two health endpoints. Both are unauthenticated — no Bearer token required.

## GET /health

Basic liveness probe. Returns immediately. Use this for systemd's `HealthCheck` directive and load balancer liveness checks.

```bash
curl http://localhost:4200/health
```

```json
{
  "status": "ok",
  "version": "0.1.3-alpha"
}
```

If the server process is running, this returns `200 OK`. It does not check the database.

| Status | Meaning |
|---|---|
| `200 ok` | Process is alive |
| Any error | Process is not running or not accepting connections |

## GET /health/detailed

Full readiness probe. Checks the database connection, reports version details, and counts active provider keys. Use this for load balancer readiness checks and monitoring dashboards.

```bash
curl http://localhost:4200/health/detailed
```

```json
{
  "status": "ok",
  "version": "0.1.3-alpha",
  "build_time": "2026-05-12T07:00:00Z",
  "commit": "b176ba2",
  "database": "connected",
  "db_latency_ms": 2,
  "provider_keys": 3,
  "uptime_seconds": 86423
}
```

| Field | Description |
|---|---|
| `status` | `ok` or `degraded` |
| `version` | Qorven version string |
| `build_time` | Binary build timestamp |
| `commit` | Git commit hash |
| `database` | `connected` or `unavailable` |
| `db_latency_ms` | Roundtrip to the database in milliseconds |
| `provider_keys` | Number of configured provider API keys |
| `uptime_seconds` | Time since the process started |

When the database is unavailable, `status` is `degraded` and the endpoint returns `503 Service Unavailable`:

```json
{
  "status": "degraded",
  "version": "0.1.3-alpha",
  "database": "unavailable",
  "error": "connection refused"
}
```

<Info>
  The web UI uses `/health/detailed` to display the version number in the status bar. It fetches this endpoint directly, not through the `/v1/` API prefix.
</Info>

## Expected response time

Both endpoints should respond in under 100 ms. `/health` is typically under 5 ms. If `/health/detailed` is slow, the database may be under load.

## Use in systemd

The installer configures a `HealthCheck` directive in the systemd unit:

```ini
[Service]
ExecStartPost=/bin/sh -c 'until curl -sf http://localhost:4200/health; do sleep 1; done'
```

If the health check fails after startup, systemd marks the service as failed.

## Use with load balancers

Configure your load balancer to poll `http://internal-ip:4200/health` (not the public web port). A 200 response means the instance is healthy.

For zero-downtime deploys, poll `/health/detailed` and wait for `"database": "connected"` before routing traffic to a new instance.
